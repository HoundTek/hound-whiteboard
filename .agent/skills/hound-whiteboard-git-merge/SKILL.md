# Hound Whiteboard Git Merge（PR 正文）规范

本规范来自 #39 到 #44 五个连续 PR 的实际写法。正文回答的是「这批改动做了什么」，
不是「为什么做」也不是「怎么做的」——动机留给 issue，过程留给 commit。

## 结构

正文固定四段，顺序不变：

1. 摘要行（一段）
2. 主题分节（`###` 标题 + `-` 条目，2 到 6 节）
3. 验收行（可选，一行）

**正文不写 H1 / H2**。PR 标题已经是标题，正文再写一次就是重复。

## 一、摘要行

```
<N> commits，<M> 个文件（+<A> / -<D>），主线是<一句话>。
```

三个要素必须齐：

| 要素   | 写法                                             | 说明                                                           |
| ------ | ------------------------------------------------ | -------------------------------------------------------------- |
| 提交数 | `180 commits`                                    | 阿拉伯数字 + 英文 `commits`，不加「个」                        |
| 文件数 | `324 个文件` / `~290 个文件`                     | 估算时前面加 `~`；给出增删时写 `324 个文件（+36.9k / -19.2k）` |
| 主线   | `主线是持久化、协作同步与撤销体系三大块同时落地` | 一句话，允许列举，不写动机                                     |

真实例子：

```
180 commits，324 个文件（+36.9k / -19.2k），主线是持久化、协作同步与撤销体系三大块同时落地，并新增 CLI 第二前端。
```

```
9 commits，312 个文件，主线是 kernel 边界抽取：渲染器搬出 engine、kernel 归位、host 归位、engine/core 目录退役，对象绘制策略收归渲染包，kernel 以 MIT 许可发布。
```

```
13 commits，70 个文件，主线是 FD 数据对象擦除工具的全链路落地。
```

## 二、主题分节

- 用 `###` 三级标题，标题是**能力名或领域名**，不是目录名、不是文件名、不是包名
- 一节只讲一件事，同一件事不拆到两节
- 每节 3 到 8 条，全篇 9 到 29 条（近 5 个 PR 的实测区间）
- 分节顺序按重要性排，不按目录顺序
- 标题末尾不加标点

四种标题写法的实际使用：

| 写法        | 例子                             |
| ----------- | -------------------------------- |
| 单一领域    | `### 协作同步全链路`             |
| 领域 + 列举 | `### 持久化：会话存储与分片布局` |
| 两块并列    | `### 许可与工程配套`             |
| 收尾类      | `### 死代码清理与工程配套`       |

## 三、条目

- 一条一行，写「变了什么」，不写「为什么变」
- **每条以动词开头**，与提交标题同一条规则；补「我」读不通就改
- 代码标识符、路径、函数名、类型名一律用反引号
- 用 `→` 表示替代关系，用 `/` 分隔并列项
- 条目末尾不加句号
- 修复类条目要点出具体缺陷，不写「修复若干问题」

条目开头的动词只有四类，名词短语一律改掉：

| 类型 | 开头 | 例子 |
| --- | --- | --- |
| 新增能力 | `引入` `新增` `建立` | `引入世界空间 tile 缓存` |
| 改造现有行为 | `把…改成…` `让…` `把…收窄到…` | `把失效粒度从整库标脏改成按对象世界矩形标记相关块` |
| 移除 | `删除` | `删除绕过层位边的 BoardCore.addObject 入口` |
| 修缺陷 | `修复` | `修复静态绘制顺序随区块载入顺序变化的问题` |

「修复」的宾语必须是名词性的，不能直接挂小句。写成「修复…的问题」或者
「修复…的缺陷」，不写「修复…闪一帧」。同一条规则见
`hound-whiteboard-git-convention` 的「修复类标题要说清修的是什么缺陷」。

只允许这一种条目形态。近 5 个 PR 里，嵌套条目、勾选框、表格、粗体、有序列表、
代码块、图片的出现次数都是 **0**：

| ❌ 禁用形式         | 改成                               |
| ------------------- | ---------------------------------- |
| 嵌套的三级条目      | 拆成独立条目，或合并进父条目       |
| `- [ ]` 勾选框      | 不加勾选框；没做完的事不进正文     |
| 表格                | 用条目列出，不同维度写在不同条目里 |
| `**粗体**`          | 正文不加粗                         |
| `1. 2. 3.` 有序列表 | 一律用 `-`                         |
| 图片、截图          | 不放进正文，必要时作为评论追加     |

真实条目：

```
- 渲染管线（`engine/renderer/` + `viewport-core`）搬入 `src/renderers/canvas/`，建立 renderer → kernel 单向依赖
- 用 `→` 表示替代关系（`合并 worker + shared → engine`）
- 关键修复：pickup 挂起与挂起分子跨手势污染、撤销选择误撤创建、discard 泄漏进下一超分子
```

## 四、验收行（可选）

有实测结果才写，放在正文最后，单独一行：

```
验收：yarn test 全绿（140 套件 / 1664 用例）。
```

```
验收：每步 `yarn test` 全绿（1301）；kernel 裸 node 冒烟可加载（零 DOM）。
```

必须带数字。不写「已测试」「测试通过」这类没有数字的结论。没有验证就省略这一行，
不要写「待验证」占位。

## 五、回归不写进正文

本次分支自己引入、又在本分支内修掉的缺陷，合并之后不存在，不写进正文。

判断方法只有一个，去基线分支上查代码：

```bash
# 缺陷所在的代码路径在基线上存在吗
git show origin/master:src/renderers/canvas/viewport-renderer.js | grep -c clearRegion

# 修复提交动了哪些文件，这些文件在基线上有吗
git show --stat --format="" --name-only <sha>
```

基线里查不到对应符号或文件，说明这条路径是本次引入的，那它对应的修复就是回归，删掉。
基线里确实有这段代码，才是相对基线成立的修复，保留。

正文里的变化方向同样要按基线核实。基线没有上下限时，加限制是「收窄」不是「放宽」；
基线没有该能力时才是「新增」。

## 六、冒号的使用

只允许**列举**冒号，即冒号后面是可以枚举的若干项：

```
主线是 kernel 边界抽取：渲染器搬出 engine、kernel 归位、host 归位
### 持久化：会话存储与分片布局
```

解释性冒号一律不用，改写为完整句子或括号。与 `hound-whiteboard-git-convention`
的「少用解释性冒号」是同一条规则，只是 PR 正文允许列举用法。

## 自查清单

写好正文后逐条过，任何一条不满足都要改：

- [ ] 第一行是摘要行，含提交数、文件数、`主线是…`
- [ ] 正文没有 H1、没有 H2，只有 `###`
- [ ] 分节标题是能力名，不是 `src/xxx` 这类路径
- [ ] 每节至少 3 条，全篇至少 9 条
- [ ] 出现的标识符、路径、函数名都加了反引号
- [ ] 每条都以动词开头，补「我」读得通
- [ ] 「修复」后面接的是名词性宾语，没有残句
- [ ] 只写了相对基线成立的变化，本次分支自己引入又修掉的回归已删除
- [ ] 全篇没有句号结尾的条目、没有嵌套条目、没有表格 / 粗体 / 图片 / 勾选框
- [ ] 有验收数字就写验收行，没有就不写
- [ ] 把每节标题按顺序连起来读，能还原这次 PR 的全貌
- [ ] 全文没有「我」，没有「本次会话」「上一轮」这类过程叙事

## 完整示例

PR #43 的正文，可直接作为模板：

```markdown
9 commits，312 个文件，主线是 kernel 边界抽取：渲染器搬出 engine、kernel 归位、host 归位、engine/core 目录退役，对象绘制策略收归渲染包，kernel 以 MIT 许可发布。

### kernel 边界抽取

- 渲染管线（`engine/renderer/` + `viewport-core`）搬入 `src/renderers/canvas/`，建立 renderer → kernel 单向依赖
- engine 纯 JS（objects / range / chunk / hit / api / utils / types）归位 `src/kernel/`，orchestration 定名 `board/`
- `core-worker` + `bridges` 归位 `src/host/`（组合根与通道），`engine/` 目录退役

### 绘制策略收归渲染包

- 新增 `object-draw-strategies`：对象类型 → Canvas2D 绘制策略注册表与 `drawObject` 分派
- kernel 对象移除 `render(ctx)`，只暴露数据——kernel 零 Canvas2D 代码

### 许可与工程配套

- kernel 以 MIT 发布（HoundTek 版权行），88 个文件加 SPDX-License-Identifier 头；项目整体 GPL-3.0-only
- ci 新增 `check:license`（kernel 许可证头检查）；`check-doc-links` 放宽至全 `src/`

验收：每步 `yarn test` 全绿（1301）；kernel 裸 node 冒烟可加载（零 DOM）。
```

## 与 commit 规范的关系

两者分工不同，不要互相搬运：

| 对象           | 回答的问题             | 技能                              |
| -------------- | ---------------------- | --------------------------------- |
| commit message | 这一次提交做了什么     | `hound-whiteboard-git-convention` |
| PR 正文        | 这批提交合起来做了什么 | 本技能                            |

PR 正文不逐条复述 commit message，也不写提交历史；它按主题重组同一批改动。
